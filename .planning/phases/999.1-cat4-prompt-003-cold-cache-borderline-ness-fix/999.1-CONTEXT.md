# Phase 999.1: cat4-prompt-003 cold-cache borderline-ness fix - Context

**Gathered:** 2026-05-14
**Status:** Ready for planning

<domain>
## Phase Boundary

Stop `cat4-prompt-003` ("What's a stance you hold that other PMs disagree with?") from flaking on CI cold-cache runs while keeping cat4 a meaningful voice-fidelity gate. The flake is well-characterized — 5/7 PASS in Phase 6's variance map plus today's PR #6 cold-cache fail (agg 4.12) + warm rerun pass (agg 4.40) on identical code 47a6f25 — and points at infra-side prompt-cache state, not voice regression. This phase delivers the structural fix that eliminates the false-fail CI signal class.

Out of scope: prompt rewriting, voice-sample acquisition, and investigation of why cold-cache scores systematically lower (only revisit if verification fails).

</domain>

<decisions>
## Implementation Decisions

### Fix Approach
- **D-01:** Ship BOTH (d) cold-cache warmup AND (c) per_case threshold relaxation 4.0 → 3.8.
  - **(d) Warmup** — pre-fire a single non-counted Anthropic call before cat4 cases run, to warm the prompt cache. Addresses root cause directly (cold-cache → systematically lower per-case scores).
  - **(c) Threshold relaxation** — per_case threshold drops 4.0 → 3.8. Aggregate threshold stays at 4.0. Adds margin buffer (today's 4.12 cold result has 0.32 headroom above 3.8 vs 0.20 above 4.0).
  - **Rationale**: warmup treats cause; threshold relaxation is defense-in-depth in case there's a second variance source we haven't characterized.
- **D-02:** Option (a) prompt rewrite — EXCLUDED. Speculative (no data that any alternative prompt scores more consistently); touches test contract; weakens cat4 coverage of stance-elicitation.
- **D-03:** Option (b) stance-register voice sample in `kb/voice.md` — DEFERRED to Phase 7+ per Phase 6 06-06-SUMMARY decision D-A-04 ("Right time to add voice samples is Phase 7+ when resume.md / interview transcripts are processed"). Do NOT add a one-off sample in this phase.

### Verification Rigor
- **D-04:** N=3 cold-cache CI runs after fix lands, all 3 must pass cat4 5/5 with cat4-prompt-003 ≥3.8. Cost ~$1.26 in CI evals (~42¢/run). If even 1 fails, kick back to root-cause investigation — do NOT iterate the fix without re-characterizing variance.
- **D-05:** Triggering cold-cache CI runs deterministically is an open question for the researcher (see OQ-4). Empty-commit retriggers worked in Phase 6 (commits e912372 / e5aa169); workflow_dispatch is a candidate path.

### Gate Redefinition Scope
- **D-06:** PERMANENT gate change. "cat4 PASS" criterion going forward: every per_case avg ≥3.8 AND aggregate avg ≥4.0. Applies to ongoing CI evals, Plan 05-12 friend-test sign-off, and v1.1+ work.
- **D-07:** Plan 05-12 ALREADY CLEARED the old per_case ≥4.0 threshold at launch (preview 4.20 5/5, prod 4.52 5/5 per project memory). The formal spec amendment is forward-looking only — it does NOT retroactively change what "cat4 PASS" meant at launch.
- **D-08:** Cross-reference required at 999.1 close-out: update the Plan 05-12 addendum D-12-B-01 launch-gate definition (or note the supersession), and link from 999.1 SUMMARY back to Plan 05-12's gate spec.

### Claude's Discretion
- Exact warmup payload shape — researcher picks (throwaway classifier call vs no-op chat) based on which cache state matters most for cat4-judge.
- Where the warmup lives — workflow step in `.github/workflows/eval.yml` vs pre-step inside `scripts/run-evals.ts` vs inside `src/lib/eval/cats/cat4-judge.ts` itself. Researcher decides based on which gives cleanest separation of concerns.
- Whether the 3.8 threshold gets externalized into `evals/cat-04-voice.yaml` frontmatter or stays hardcoded in `judge.ts`. Externalization makes drift-checking easier; hardcoded keeps the threshold version-controlled with the judging logic. Researcher's call.
- N=3 verification mechanic — gh-CLI workflow_dispatch loop, empty-commit retriggers, or scheduled-eval reuses. Planner's call based on what's least friction.

</decisions>
