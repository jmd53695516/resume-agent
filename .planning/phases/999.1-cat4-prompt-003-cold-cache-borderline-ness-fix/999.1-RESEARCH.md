## Summary

The fix has two locked components and four open questions whose answers all converge on a single, low-risk implementation shape. The core finding: **Haiku judge calls are NOT cached** (judge prompts ~1500-1800 tokens, Haiku 4.5 minimum cache block is 4096 tokens [VERIFIED: platform.claude.com prompt-caching docs, 2026-05-14]). The cold-cache flake is therefore not about the judge — it's about the **Sonnet 4.6 main-agent call** that generates the agent response being judged. Cold-cache Sonnet replies on the stance-elicitation prompt are systematically shorter and/or less concrete, dragging concreteness and rhythm sub-scores by ~0.3, which on a 4-pass / 1-borderline case is enough to trip the 4.0 per_case floor.

**Primary recommendation:** Warmup the **Sonnet 4.6 chat path** by issuing a single throwaway POST to `<targetUrl>/api/chat` inside `cat4-judge.ts` before the case loop. Place the warmup *inside `runCat4Judge`* (OQ-1 sub-option iii), not at the workflow or CLI level, because (a) it warms the Sonnet path against the *actual target URL* the cases will hit, (b) the cost is naturally excluded from `eval_runs.total_cost_cents` because that aggregate is computed only from each runner's returned `cost_cents` field (verified in `scripts/run-evals.ts:262`), and (c) local-dev repro stays identical to CI repro. Externalize the 3.8 threshold to `evals/cat-04-voice.yaml`'s existing `pass_threshold.per_case_min_avg` key (OQ-3) — that key already exists, just change `4.0` → `3.8`, and `cat4-judge.ts` reads it instead of the hardcoded `PASS_THRESHOLD = 4.0`. For N=3 verification, use `gh workflow run eval.yml -f target_url=https://joe-dollinger-chat.com -f cats=cat4-judge` (OQ-4) — workflow_dispatch grants each run a fresh ubuntu-latest runner with no Anthropic cache state from prior runs, satisfies cold-cache deterministically, and at ~12¢/run × 3 = ~36¢ is well under the D-04 budget of ~$1.26.

**Net change surface:** ~30 LOC in `src/lib/eval/cats/cat4-judge.ts` (warmup helper + threshold read from YAML), ~3 LOC in `evals/cat-04-voice.yaml` (one numeric edit + a comment), 0 LOC in workflow files, 0 LOC in `judge.ts` (it never had the `4.0` constant — that lives in `cat4-judge.ts:35`).

### Pattern 1: In-Runner Pre-step Warmup

**What:** A single `await warmupSonnetCache(targetUrl)` call at the top of `runCat4Judge`, before `for (const c of cases)`.
**When to use:** When the warmup is conceptually *part of the category's setup*, not a global concern, AND when the runner already touches the same surface that needs warming.
**Why here:** cat4-judge is the only category that has demonstrated cold-cache flake. Other cats (cat1, cat2, cat3, cat5, cat6) get their own first-call cold-cache penalty but it doesn't tip per-case strict thresholds because their gates aren't per-case-Likert-floor based. Putting warmup in `runCat4Judge` correctly scopes it.

**Example:**

```typescript
// src/lib/eval/cats/cat4-judge.ts (proposed)
// Source: in-repo pattern; mirrors /api/cron/heartbeat HEARTBEAT_LLM_PREWARM approach (Plan 04-07)

/**
 * Warm the Anthropic prompt-cache for the Sonnet 4.6 main-agent path that
 * cat4 cases exercise. The cat4-prompt-003 cold-cache flake (Phase 6 N=7
 * variance map: 5/7 PASS) traces to Sonnet 4.6 cold-cache responses on
 * stance-elicitation being ~0.3 less concrete than warm-cache responses.
 *
 * Strategy: issue ONE throwaway POST to /api/chat against the same targetUrl
 * the cases will hit. The Anthropic prompt cache attaches to the system
 * prompt (~85k tokens, well above the 1024-token Sonnet minimum cache block
 * [VERIFIED: platform.claude.com/docs/en/build-with-claude/prompt-caching]),
 * so a single completed call writes the cache; the 5 cat4 cases that follow
 * within ~75 seconds will hit a warm cache (default 5-min TTL — well above
 * the cat4 runtime of ~75s).
 *
 * COST-REPORTING ISOLATION: this function's cost is NOT added to the
 * CategoryResult.cost_cents return value. eval_runs.total_cost_cents is
 * computed by scripts/run-evals.ts:262 as
 *   results.reduce((s, r) => s + r.cost_cents, 0)
 * — only the per-runner returned cost_cents counts. The warmup's tokens
 * are paid by Anthropic billing but invisible to the eval_runs cost row.
 * This is the desired posture per CONTEXT OQ-1: "warmup MUST NOT count
 * against eval cost rows."
 */
async function warmupSonnetCache(targetUrl: string, sessionId: string): Promise<void> {
  try {
    const res = await fetch(`${targetUrl}/api/chat`, {
      method: 'POST',
      headers: { 'content-type': 'application/json' },
      body: JSON.stringify({
        session_id: sessionId,
        messages: [
          {
            id: 'eval-warmup-1',
            role: 'user',
            parts: [{ type: 'text', text: 'warmup ping' }],
          },
        ],
      }),
    });
    // Drain the response body so the underlying fetch promise resolves and
    // the connection can be reused. We don't care about the content.
    await res.text();
    log.info({ sessionId, status: res.status }, 'cat4_warmup_complete');
  } catch (err) {
    // Best-effort: a failed warmup must not fail the cat4 run. Log + proceed.
    log.warn(
      { err: (err as Error).message },
      'cat4_warmup_failed_proceeding_anyway',
    );
  }
}
```

### Pattern 2: YAML-Driven Threshold

**What:** Read `pass_threshold.per_case_min_avg` from `evals/cat-04-voice.yaml` at runner startup instead of using the hardcoded `PASS_THRESHOLD = 4.0` constant.
**When to use:** When the rubric YAML already declares the constraint (it does — `cat-04-voice.yaml:42`) and the runtime currently ignores it. Resolve drift.
**Why here:** The YAML *already* states `per_case_min_avg: 4.0` (line 42); the runner *already* hardcodes `PASS_THRESHOLD = 4.0` (line 35). These two are drifting copies of the same truth. Externalizing reduces to one source AND satisfies the D-06 amendment for free — future drift-checking during EVAL-12 monthly calibration becomes a single-file diff [VERIFIED: cat-04-voice.yaml:41-44 + cat4-judge.ts:35-36].

**Example:**

```typescript
// Proposed addition near top of src/lib/eval/cats/cat4-judge.ts
interface Cat4Config {
  passThreshold: number;       // per_case_min_avg from YAML
  aggregateThreshold: number;  // aggregate_min_avg from YAML
  voiceSamplesCount: number;   // voice_samples_count from YAML
}

async function loadCat4Config(): Promise<Cat4Config> {
  const filepath = path.join(process.cwd(), 'evals', 'cat-04-voice.yaml');
  const raw = await readFile(filepath, 'utf8');
  const parsed = yaml.parse(raw) as {
    pass_threshold: {
      per_case_min_avg: number;
      aggregate_min_avg: number;
      n_cases: number;
    };
    voice_samples_count: number;
  };
  return {
    passThreshold: parsed.pass_threshold.per_case_min_avg,
    aggregateThreshold: parsed.pass_threshold.aggregate_min_avg,
    voiceSamplesCount: parsed.voice_samples_count,
  };
}
```

### Anti-Patterns to Avoid

- **Hardcoding 3.8 in cat4-judge.ts AND leaving 4.0 in cat-04-voice.yaml.** This creates the exact "two-sources-of-truth drift" that prompted the original concern at OQ-3. Don't do it. If the planner chooses hardcoded over YAML, also update the YAML constant for self-documentation.
- **Putting warmup at workflow level (eval.yml step).** Local-dev repros (e.g., a future Joe running `npm run eval --cats=cat4-judge` to debug a failing CI run) would behave differently from CI — losing the "single fix; same path everywhere" property. See OQ-1 analysis.
- **Adding warmup cost to `totalCost` inside `runCat4Judge`.** Defeats the cost-isolation invariant in CONTEXT OQ-1 ("warmup MUST NOT count against eval cost rows"). The recommended pattern (warmup before the case loop, never touching `totalCost`) handles this automatically.
- **Forgetting to mint a session for the warmup call.** /api/chat (Phase 5 BL-17 hardening) validates `session_id` against Supabase; an unknown session returns 404. Solution: pass the *same* `sessionId` minted by `mintEvalSession(targetUrl)` (which `runCat4Judge` already mints at line 72) to `warmupSonnetCache`.

### OQ-1: Where should the warmup live?

**Recommendation: (iii) Inside `src/lib/eval/cats/cat4-judge.ts`** at the top of `runCat4Judge()`, before the case loop.

**Justification on the four CONTEXT-stated dimensions:**

| Dimension | (i) eval.yml step | (ii) run-evals.ts pre-step | (iii) cat4-judge.ts inline (RECOMMENDED) |
|-----------|-------------------|---------------------------|------------------------------------------|
| Separation of concerns | Bad: workflow YAML now reasons about Anthropic semantics. CI tooling concern leaks into model concerns. | OK: orchestrator does setup; reasonable. But warmup is cat4-specific noise in a multi-cat orchestrator. | **Best:** warmup lives with the runner that needs it. Other cats don't pay the warmup cost or read the warmup code. |
| Cost-reporting isolation (warmup tokens MUST NOT count) | OK: the warmup call happens before `npm run eval` exits; not summed by `run-evals.ts:262`. | OK: same — pre-step happens outside the runners' returned `CategoryResult.cost_cents`. | **OK:** function does not modify `totalCost` accumulator; the `cost_cents` returned by `runCat4Judge` is computed from `judgeVoiceFidelity` results only. [VERIFIED: cat4-judge.ts:84 `let totalCost = 0` only incremented from `judge.cost_cents` at line 102] |
| Local-dev repro story | Bad: CI runs warm, `npm run eval --cats=cat4-judge` locally does not. Two execution paths diverge. | OK: same path everywhere `run-evals.ts` is the entrypoint (which is *always* — both CI and local). | **Best:** same as (ii), with the additional benefit that the warmup is impossible to "skip" by running individual runner tests. |
| CI-only-vs-everywhere semantics | CI-only by construction (lives in workflow file). | Everywhere — fires on every `npm run eval` regardless of `--cats` filter. Wasteful when running cat1-only or cat6-only. | **Everywhere it matters:** warmup fires only when cat4-judge runs (`if (filter.has('cat4-judge'))` is implicitly the gate, since `runCat4Judge` is the entry point). Other cat runs pay no warmup cost. |

**Operational note:** Putting warmup in `cat4-judge.ts` means warming happens *after* `mintEvalSession` (line 72) so the warmup can reuse the same `sessionId`. The session is created once per category — the warmup POST is a 6th request on that session, comfortably under the per-session safety net.

**TTL math:** Anthropic default cache TTL = 5 min [VERIFIED: platform.claude.com prompt-caching docs]. cat4-judge total wall-clock across the 5 cases = ~75 seconds (Plan 06-06 verification log line 104: duration 74919 ms). 75s ≪ 300s default TTL — warmup at t=0 keeps all 5 cases inside the cache window with ~225s of headroom. **No need for 1-hour extended TTL** (which would double input token price). If parallel parameter scans ever push cat4 beyond 5 min total, revisit.

### OQ-2: What payload should the warmup call use?

**Recommendation: (ii) A throwaway POST to `<targetUrl>/api/chat` (Sonnet path).** Not Haiku. Not both.

**Justification — which Anthropic cache layer is actually consumed during cat4 case execution?**

The cat4-judge pipeline has two distinct Anthropic surfaces:

1. **Sonnet 4.6 main-agent call.** `callAgent()` (agent-client.ts:134) POSTs to `/api/chat`, which `streamText`s a Sonnet 4.6 response with `buildSystemPrompt()` as the system message and `cache_control: ephemeral` attached. System prompt is ~85,373 chars / ~21,000 tokens [VERIFIED: STATE.md Phase 03 entry "system-prompt grew from 84,477 → 85,373 chars"]. **This is well above the 1024-token Sonnet minimum cache block** [VERIFIED: platform.claude.com prompt-caching docs] — every call genuinely caches. Cold-cache run pays ~$0.08 cache_write; warm-cache run pays ~$0.006 cache_read.

2. **Haiku 4.5 judge call.** `judgeVoiceFidelity()` (judge.ts:215) sends ~1500-1800 input tokens to Haiku with NO `cache_control` directive. **Haiku minimum cache block is 4096 tokens** [VERIFIED: platform.claude.com prompt-caching docs — corrects CLAUDE.md which says "2048" — that figure refers to a prior model version; the 4.5 minimum is 4096]. Judge prompts are **always below the threshold** — Haiku judge calls are **never cached, period**. There is no warm/cold cache distinction on the Haiku surface.

**Conclusion:** The cold-cache variance source is the Sonnet 4.6 path, not the Haiku judge path. Warming Haiku is impossible at our judge prompt size; warming Sonnet is the only meaningful action.

**Why "POST to /api/chat" specifically (vs a direct SDK call to Anthropic)?** Anthropic's cache hit requirement is *byte-identical prefix* [VERIFIED: platform.claude.com — "Cache hits require 100% identical prompt segments"]. The only way to write a cache entry that the cat4 cases will actually hit is to call through the same code path (`buildSystemPrompt()` + `streamText` config + `cache_control: ephemeral`) that the cases use. A bespoke SDK call would generate a different prefix hash and warm a different (useless) cache slot.

**Prompt text for the warmup:** Any short user message works (the cache is on the *system prompt prefix*, not the user message). Recommended: `"warmup ping"` or `"hi"` — keep it under 10 tokens to minimize Sonnet output cost. The classifier will likely tag it `offtopic` and trigger a deflection — that's fine; the deflection path *still* runs through the system prompt and *still* writes the cache entry. (NOTE: needs planner-verify against `route.ts:87-99` deflectionResponse path — if deflection short-circuits before the Anthropic call, swap to a "tell me about yourself" prompt that will route through Sonnet.) **Planner action:** confirm this by reading `src/app/api/chat/route.ts` lines 87-99 + 200-260 (the gate ordering); if deflection skips Sonnet, use a benign prompt that the classifier passes (e.g. `"Tell me one thing about your background."`).

**Cost:** Warmup is ~1 Sonnet call: ~85k tokens cache_write @ $3.75/MTok = $0.32 + ~150 output tokens @ $15/MTok = $0.002 → **~$0.32 per warmup** (~32¢). Same order of magnitude as one CI eval run (~42¢/run) — but invisible to `eval_runs.total_cost_cents` because the warmup is outside the cost accumulator (verified above). Anthropic org-level $20/mo cap absorbs it.

### OQ-4: How to trigger N=3 cold-cache CI runs deterministically?

**Recommendation: `gh workflow run eval.yml -f target_url=https://joe-dollinger-chat.com -f cats=cat4-judge` × 3.**

**Why this beats empty-commits and natural-merge wait:**

| Mechanic | Cold-cache reliability | Git pollution | Cost per run | Operational effort |
|----------|------------------------|---------------|--------------|---------------------|
| Empty-commit retrigger (Phase 6 pattern) | HIGH — each push triggers Vercel deploy + new GH Actions runner | 3 empty commits in git log | ~42¢/run (full narrowed gate: cat1+cat4-judge) | `git commit --allow-empty -m "retrigger" && git push` × 3, plus deferred-item bookkeeping |
| **workflow_dispatch (RECOMMENDED)** | **HIGH — each dispatch gets a fresh ubuntu-latest runner with no shared Anthropic cache** | **Zero commits** | **~12¢/run (cat4-judge only, per CONTEXT)** | **One `gh` command × 3** |
| Natural-merge wait | HIGH but uncontrolled timing | Zero commits | Free (incidental) | Slow; couples 999.1 verification to unrelated PR merges; not deterministic timing |
| Scheduled-eval reuse | HIGH | Zero commits | ~42¢/run (full narrowed gate) | Wait days for weekly schedules; not deterministic |

  -f target_url=https://joe-dollinger-chat.com \

## Cost-Reporting Isolation (deep dive)

**The question:** How does the eval runner currently aggregate Anthropic spend into `eval_runs` rows? Does the warmup call's tokens inflate this aggregate?

**Code path traced:**

1. **`eval_cases.cost_cents`** (per-case spend) — written by `writeCase()` (`src/lib/eval/storage.ts:34`). For cat4-judge, populated from `judge.cost_cents` (judge call cost only) at `cat4-judge.ts:116`. **The Sonnet main-agent call's cost is NOT written here** — `callAgent()` in agent-client.ts has no usage extraction; it just reads the text stream. So the per-case cost row already excludes Sonnet cost.

2. **`eval_runs.total_cost_cents`** (per-run aggregate) — written by `updateRunStatus()` (`storage.ts:59`). Source: `totalCostCents = results.reduce((s, r) => s + r.cost_cents, 0)` (`run-evals.ts:262`). **Each runner's `CategoryResult.cost_cents`** is the sum of its per-case judge costs only.

3. **Per-runner `CategoryResult.cost_cents`** for cat4-judge — computed inside `runCat4Judge` as `Math.round(totalCost)` where `totalCost` is incremented only by `judge.cost_cents` (line 102). **Warmup `fetch()` cost would NOT be in this sum** unless explicitly added.

**Conclusion:** As long as `warmupSonnetCache` does NOT increment `totalCost` (the local variable inside `runCat4Judge`), the warmup's Anthropic token spend is invisible to both `eval_cases.cost_cents` and `eval_runs.total_cost_cents`. The recommended implementation never touches `totalCost`. **Isolation property: HELD by construction.**

**Where the warmup cost IS visible:**
- Anthropic billing dashboard (real money charged)
- Vercel /api/chat logs (the warmup POST shows up as a regular chat request)
- SAFE-04 daily spend cap counter (Upstash Redis `resume-agent:spendcap:...`) — *if* `SAFETY_GATES_ENABLED=true`, the warmup's Sonnet cost would be tracked against the daily $3 cap. **Important:** kill-switch is OFF by default (260512-tku) so this isn't an issue today, BUT if 999.1 ships with the warmup *while the kill-switch is also flipped back ON by SEED-002* (per "before broad distribution" trigger), then ~32¢ × 3 = ~$1 of warmup cost on top of ~$1.26 eval cost = ~$2.26 against the $3 cap. **Planner action:** flag this dependency on SEED-002 timing — if 999.1 lands BEFORE SEED-002 re-enable, no issue; if AFTER, verify the per-IP spend-cap allowlist (`isEmailSpendCapAllowlisted('eval-cli@joedollinger.dev')`) covers the warmup-as-eval-cli pattern.

## Common Pitfalls

### Pitfall 1: Warming the wrong cache slot
**What goes wrong:** Calling Anthropic directly via `@anthropic-ai/sdk` with a hand-rolled system prompt — different prefix hash, different cache slot, zero help to subsequent /api/chat calls.
**Why it happens:** "I'll just call Anthropic to warm the cache" is faster to write than "fetch /api/chat with a dummy prompt."
**How to avoid:** Always warm by calling the *same code path* the cases will hit. For cat4-judge, that's `/api/chat`.
**Warning signs:** N=3 verification still flakes despite warmup. First step: log `cache_read_input_tokens` and `cache_creation_input_tokens` on the case-1 Sonnet call — if cache_read is 0, the warmup didn't take.

### Pitfall 2: Forgetting to mint a session for the warmup
**What goes wrong:** `/api/chat` returns 404 because `session_id` not in Supabase (BL-17 hardening). Warmup fails silently (because of the try/catch), and the cases run cold-cache.
**Why it happens:** Devs reading `agent-client.ts` see `callAgent()` and forget that `mintEvalSession()` must precede it.
**How to avoid:** In `runCat4Judge`, the order must be: (1) `loadCases`, (2) `loadVoiceSamples`, (3) `mintEvalSession`, (4) **`warmupSonnetCache(targetUrl, sessionId)`**, (5) case loop. Add a `log.info({ status })` inside the warmup to surface 404s loudly.
**Warning signs:** Log line "cat4_warmup_failed_proceeding_anyway" with status=404.

### Pitfall 3: YAML threshold drift
**What goes wrong:** Planner edits the YAML but not the runner, OR the runner but not the YAML. Two sources of truth diverge.
**Why it happens:** The current state IS the drift — runner and YAML both claim 4.0 independently. The fix touches both files; a careless commit could touch only one.
**How to avoid:** Stage both `evals/cat-04-voice.yaml` and `src/lib/eval/cats/cat4-judge.ts` in the same commit. Add a regression test: `loadCat4Config()` returns `{ passThreshold: 3.8, aggregateThreshold: 4.0 }` (asserts the YAML is the source of truth and the runner reads it).
**Warning signs:** `grep PASS_THRESHOLD src/lib/eval/cats/cat4-judge.ts` returns any line with `= 4.0` after the change.

### Pitfall 4: Cold-cache TTL drift
**What goes wrong:** A future cat4-judge change (more cases, longer judge prompts) pushes total runtime past 5 min, breaking the warmup→case TTL invariant.
**Why it happens:** Future Joe adds a 6th cat4 case without re-doing the TTL math.
**How to avoid:** Document the 5-min TTL constraint as an inline comment in `runCat4Judge` near the warmup call. Add a runtime assertion: if `Date.now() - warmupStart > 240_000` (4 min, 1-min safety margin), log a warning.
**Warning signs:** cat4-judge cases late in the loop start failing again with cold-cache patterns.

### Pitfall 5: SAFE-04 spend-cap collision (if SEED-002 re-enabled)
**What goes wrong:** Warmup adds ~32¢ per run to Anthropic spend; if `SAFETY_GATES_ENABLED=true` AND warmup happens before allowlist short-circuit, the SAFE-04 daily cap could trip mid-eval.
**Why it happens:** SEED-002 re-enables gates "before broad distribution" — if that happens between 999.1 merge and N=3 verification, the gates are live during verification.
**How to avoid:** Verify `isEmailSpendCapAllowlisted('eval-cli@joedollinger.dev')` returns `true`; the warmup POST passes `session_id` minted with `email: 'eval-cli@joedollinger.dev'`, so the allowlist applies.
**Warning signs:** Warmup POST returns 429 with body referencing spend-cap deflection.

### Pitfall 6: Empty-commit retrigger pattern leaks into N=3 verification
**What goes wrong:** Executor falls back to Phase 6's empty-commit pattern instead of `gh workflow run`. Result: 3 noise commits in main's log + a redeploy each time + the commits are time-stamped close together so cache state may bleed run-to-run.
**Why it happens:** Phase 6 set the precedent; muscle memory.
**How to avoid:** Plan explicitly specifies `gh workflow run eval.yml -f target_url=... -f cats=cat4-judge` × 3. Reject any plan that uses empty-commits for N=3 verification.
**Warning signs:** `git log --oneline -5` after 999.1 shows "retrigger eval" commits.

## Code Examples

### Verified pattern: in-runner warmup (proposed for cat4-judge.ts)

```typescript
// Source: synthesized from /api/cron/heartbeat (Plan 04-07) + agent-client.ts callAgent
//         Anthropic prompt-caching docs: https://platform.claude.com/docs/en/build-with-claude/prompt-caching

async function warmupSonnetCache(
  targetUrl: string,
  sessionId: string,
): Promise<void> {
  try {
    const res = await fetch(`${targetUrl}/api/chat`, {
      method: 'POST',
      headers: { 'content-type': 'application/json' },
      body: JSON.stringify({
        session_id: sessionId,
        messages: [
          {
            id: 'eval-warmup-1',
            role: 'user',
            // NOTE: planner must verify this prompt routes through Sonnet (not
            // short-circuited by the classifier deflection path). If the
            // classifier flags 'warmup ping' as offtopic, deflectionResponse()
            // emits a data-deflection chunk and may skip the Anthropic call.
            // Safer alternative: a benign on-domain prompt.
            parts: [{ type: 'text', text: 'Tell me one thing about your background.' }],
          },
        ],
      }),
    });
    await res.text(); // drain body so connection can close
    log.info({ sessionId, status: res.status }, 'cat4_warmup_complete');
  } catch (err) {
    // Best-effort: a failed warmup must not fail the cat4 run.
    log.warn(
      { err: (err as Error).message },
      'cat4_warmup_failed_proceeding_anyway',
    );
  }
}
```
